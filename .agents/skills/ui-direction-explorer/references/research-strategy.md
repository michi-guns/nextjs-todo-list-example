# Research Strategy

Research is used to improve hypotheses, not to decorate a moodboard.

## Research questions

Start from the product problem:

- What task is the user performing?
- How frequently?
- How much information must they process?
- What errors are costly?
- Is the user novice, occasional, or expert?
- Is the interaction transactional, exploratory, monitoring-oriented, creative, or guided?
- Which comparable products have solved similar constraints?

Search using task and workflow language rather than aesthetic adjectives.

Better:

- merchant transaction filtering
- device onboarding verification
- subscription upgrade comparison
- dense audit-log inspection

Worse:

- beautiful dashboard
- modern dark UI
- cool SaaS screen

## Evidence hierarchy

Prefer evidence in roughly this order:

1. The project's existing product behavior and user constraints.
2. Real shipped interfaces solving comparable problems.
3. End-to-end user flows.
4. Established interaction conventions.
5. Visual-language references.
6. Component libraries and implementation examples.

## Research ledger

For each useful reference, capture only what matters:

- source/product
- problem being solved
- observed pattern
- why it is relevant
- what aspect may transfer
- what should not be copied
- URL or retrievable source identifier when available

A reference that cannot answer "why is this relevant?" should not drive a direction.

## Anti-anchoring rules

Do not let a famous product become the default answer.

- Prefer several relevant references over one hero reference.
- Extract principles before sketching exact layouts.
- Avoid direction names like "Stripe style" or "Linear clone."
- Do not reproduce proprietary copy, assets, illustrations, or distinctive compositions.
- If several references use the same pattern, distinguish whether it is a broadly useful convention or merely a trend.

A strong direction synthesizes observations from multiple places plus the project's own constraints.

## Stop condition

Research is sufficient when additional sources are no longer changing:

- the important constraints
- the candidate hypotheses
- the meaningful trade-offs

Do not browse indefinitely for marginally prettier examples.

## No external access

If web/MCP access is unavailable or prohibited:

1. Use the existing project as the primary evidence source.
2. Use bundled archetypes and UX heuristics to expand the search space.
3. Be explicit that external inspiration was not checked.
4. Continue the exploration; do not block.
