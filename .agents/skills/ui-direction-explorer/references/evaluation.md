# Evaluation

Evaluation exists to clarify trade-offs, not to create a fake objective winner.

## Derive criteria from the product

Do not use one fixed weighted rubric for every surface. Infer which qualities matter from the exploration contract.

Common criteria include:

- task clarity
- task throughput
- information hierarchy
- scanability
- cognitive load
- learnability
- discoverability
- error prevention / recovery
- state visibility
- accessibility
- scalability with more data/features
- responsive suitability
- consistency with the product
- brand/product character
- implementation complexity
- maintainability

Choose a small set that genuinely differentiates the directions.

## Product-type emphasis

### Operational / expert tools

Usually emphasize:

- throughput
- scanability
- state visibility
- density efficiency
- error prevention
- keyboard/bulk workflows where relevant

### Onboarding / setup / rare tasks

Usually emphasize:

- comprehension
- confidence
- progress visibility
- cognitive load
- recovery from mistakes

### Analytics / monitoring

Usually emphasize:

- hierarchy
- anomaly visibility
- comparison
- context preservation
- scalability with more data

### Consumer transactional flows

Usually emphasize:

- clarity
- trust
- completion friction
- feedback
- recovery
- mobile suitability

### Creation / productivity tools

Usually emphasize:

- state continuity
- efficiency
- focus
- direct manipulation
- discoverability of advanced capability

These are starting points, not fixed formulas.

## Rating style

Prefer qualitative ratings such as:

- Strong
- Mixed
- Weak

A simple 1–5 scale is acceptable when it improves comparison, but every rating should have a short reason.

Avoid false precision such as 87.3/100 unless the developer explicitly requests quantitative scoring and there is a defensible measurement basis.

## Recommendation rule

Recommend a direction only when the exploration contract provides enough evidence to justify it.

Otherwise identify the unresolved product choice:

> If expert throughput is the priority, A is strongest. If this workflow is mostly used by occasional operators, B has the safer interaction model.

This is a successful result; uncertainty should be exposed rather than hidden.

## Hybridization rule

Do not automatically recommend "combine the best parts." A transferable element is useful only if it preserves the receiving direction's core hypothesis.

When proposing a transfer, state why the element is compatible.
